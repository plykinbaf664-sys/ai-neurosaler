# AI-карта бизнеса: запуск и проверка

Реализован путь: `/start → AI-карта → 5 ответов → 3 процесса → самостоятельный тест → существующая библиотека / разбор с Александром`. Обычные AI для жизни и AI для бизнеса доступны без диагностики. Старые marketing callbacks, стадии и scoring сохранены.

## Порядок запуска

1. Для production использовать существующий `STORAGE_DRIVER=supabase`. Применить все недостающие миграции по порядку, включая `015_dynamic_library.sql` и затем `016_ai_map_and_visuals.sql`. Не повторять старые data migrations без необходимости. 016 аддитивная и повторяемая. Local file сохраняет состояние между перезапусками одного сервера; `LOCAL_DATA_MODE=memory` предназначен для временных/тестовых данных и не сохраняет claims после restart.
2. Сначала выложить код с новыми функциями выключенными, либо применить 016 перед включением флагов. При `AI_MAP_ENABLED=false` и `IMAGE_GENERATION_ENABLED=false` новая версия не требует новых колонок для старых сценариев.
3. Настроить ENV ниже и выполнить redeploy. Проверить доступность активных library materials и настоящих Telegraph URL. Для подписанных переходов нужен существующий `LIBRARY_LINK_SECRET` (минимум 24 символа), стабильный `PUBLIC_BASE_URL` и прежний `CALENDAR_LINK`.
4. В `vercel.json` оставлены совместимые с Hobby ежедневные задачи: gift-followups — `0 12 * * *`, library-followups — `15 12 * * *` (UTC). Они не блокируют deploy. Для +1/+3-часовых follow-up настроить внешний scheduler на существующий endpoint по инструкции ниже. Один ежедневный запуск не обеспечивает эти интервалы; после простоя обработчик отправляет только последний наступивший шаг. Отдельная очередь не нужна, claims сохраняют защиту от дублей при пересечении внешнего и ежедневного запуска.
5. Проверить новым Telegram-пользователем. Не использовать production-рассылку для технических проверок.

## Новые ENV

| ENV | Значение / действие |
|---|---|
| `AI_MAP_ENABLED` | `true`: новый onboarding и карта; `false`: старое меню/quiz/gift по прежним флагам. При включении карты обе библиотеки доступны даже если старый `LIBRARY_ENABLED=false`. Для сохранения библиотеки после выключения карты оставить `LIBRARY_ENABLED=true`. |
| `WELCOME_VIDEO_ENABLED` | `true` включает кружок на `/start`; `false` выключает. |
| `WELCOME_VIDEO_NOTE_FILE_ID` | Telegram file_id кружка, полученный от этого же бота. Пустое значение безопасно. |
| `ADMIN_TELEGRAM_ID` | Необязательный отдельный admin для media capture. Если пусто, используется существующий `TELEGRAM_ADMIN_USER_ID`; дублировать ID не нужно. Явное значение заменяет fallback только для media capture. |
| `QUIZ_FOLLOWUPS_ENABLED` | `true`: 4 сообщения по карте; `false`: пауза отправки. Требует также `AI_MAP_ENABLED=true`. Не зависит от `LIBRARY_FOLLOWUPS_ENABLED`. |
| `IMAGE_GENERATION_ENABLED` | `true`: генерация/переиспользование визуалов; `false`: текстовый flow. |
| `IMAGE_PROVIDER` | `openai`: реализованный Images API adapter. Текстовый Qwen/Anthropic не меняется. |
| `IMAGE_MODEL` | Например `gpt-image-1.5`, модель с доступом в аккаунте и поддержкой image generations/base64. |
| `IMAGE_API_KEY` | Необязательный отдельный ключ для изображений. Если пусто, используется существующий `OPENAI_API_KEY`; дублировать ключ не нужно. Нужен только для экранов без готовой картинки. Для показа кеша не требуется. Не использует ключ Qwen/Anthropic. |

Флаги читаются из ENV. После изменения переменных в hosting требуется redeploy/restart. Секреты не добавлять в git.

## Как добавить welcome video note

1. Если свой числовой Telegram ID уже задан в `TELEGRAM_ADMIN_USER_ID`, повторно добавлять его не нужно. `ADMIN_TELEGRAM_ID` заполнять только для отдельного media admin. Выложить новую версию.
2. В личном чате с **этим ботом** записать и отправить обычный кружок. Группа и отдельная админка не нужны.
3. Бот ответит `🎬 VIDEO_NOTE_FILE_ID` и следующей строкой — идентификатор.
4. Скопировать его в `WELCOME_VIDEO_NOTE_FILE_ID`, выставить `WELCOME_VIDEO_ENABLED=true`, выполнить redeploy.
5. Отправить `/start`: кружок должен прийти перед onboarding. Если ID неверный, текст и кнопки всё равно доступны. Фото от admin аналогично возвращает `🖼 PHOTO_FILE_ID`, но для штатных визуалов ручная загрузка не нужна.

## Визуалы и fallback

Экраны: onboarding, вход в life/business, результат по приоритетному процессу и три ключевых материала (потерянные лиды, договорённости команды, отзывы). К техническим сообщениям картинки не добавляются.

`screen_key + bot identity hash + visual version → telegram_visual_assets`. Prompt использует тип, заголовок, описание, категорию, slug и общий editorial-стиль; личные ответы не передаются image provider. В таблице хранятся только file_id и lease, без самих картинок. На первом открытии экран генерируется один раз и получает сохранённый Telegram file_id; последующие пользователи и открытия получают ту же картинку, в том числе после restart/deploy. Одновременные открытия имеют один generation claim; остальные продолжаются текстом.

Сначала читается кеш. Для готовой картинки provider, model и API key больше не нужны; их смена или удаление не вызывает повторную генерацию. `IMAGE_GENERATION_ENABLED=true` оставляют включённым для показа картинок. Генератор использует `IMAGE_API_KEY`, а если он пуст — `OPENAI_API_KEY`. Для новых незаполненных экранов нужен один из этих ключей; если обоих нет, такие экраны будут текстовыми. Общий ключ удалять после заполнения кеша не требуется: готовые картинки повторно не генерируются. Старые assets из первоначального model-dependent кеша автоматически переносятся при первом открытии с прежними настройками provider/model.

Image request ограничен 20 секундами, отправка media — 8 секундами. Ошибка логируется, текст продолжает работать. Ошибка генерации/загрузки даёт cooldown 24 часа, зависший claim — 5 минут; немедленных retries нет. Неисправная конфигурация не создаёт кеш. Отдельный бот имеет отдельные assets; смена модели и ротация секретной части Telegram token не сбрасывают готовые картинки. Генерация может тарифицироваться provider; live-доступ зависит от аккаунта.

## Диагностика и персонализация

Аудит старого marketing quiz:

| Вопрос | Scoring / branching | Использование |
|---|---|---|
| Заявки в месяц | A–D = 0–3 | Сумма определяет старый verdict; переход q1→q2 |
| Понимание выручки | A–D = 0–3 | Та же сумма; переход q2→q3 |
| Обработка заявок | A–D = 0–3 | Та же сумма; старый post-quiz flow |

Все старые вопросы влияют на результат; удалённых вопросов нет. Изменены формулировки и подписи, ключи/баллы/стадии сохранены. Этот узкий квиз не содержит достаточно контекста для широкой карты бизнеса, поэтому новый основной CTA запускает пять коротких вопросов, а старый `nav:marketing` обслуживается прежним кодом.

В новой карте первый ответ задаёт бизнес-контекст. Остальные четыре задают боль, зависимость от владельца, ручную работу и желаемый результат. Приоритеты определяются детерминированно с весами 4/2/3/3, без суммирования с legacy scoring. Все ответы сохраняются вне ограниченной истории сообщений. При равенстве используется стабильный порядок; №1 — рекомендация для ручного теста, не диагноз. Направления без подтверждения явно помечаются как гипотезы. Материалы берутся только из активного каталога по реальным slug; если точного материала для процесса нет, остаётся самостоятельная инструкция, выдуманных материалов нет.

Полная карта сохраняется в `user_library_profiles.ai_map` и открывается повторно основной кнопкой. Выбранные материалы становятся текущим маршрутом через существующий `recommended_material_ids`; цель берётся из ответа о желаемом результате. Повторное открытие сохранённой карты не перезаписывает последующие изменения маршрута. Рекомендация не меняет completed state, прогресс или награды. Коммерческий оффер после разбора хранится в `IMPLEMENTATION_OFFER` и используется диалогом только по запросу о внедрении: один процесс за 10 рабочих дней, БЫЛО → СТАЛО по реальным данным.

## Follow-up

### Запуск на Vercel Hobby

Hobby допускает только ежедневные Vercel Cron Jobs. Не ставить `*/5 * * * *` в `vercel.json`: такое расписание блокирует deploy. Частый запуск выполняется внешним HTTP scheduler, а существующие Vercel jobs остаются ежедневной страховкой.

Готовые настройки внешней задачи:

| Поле | Значение |
|---|---|
| URL | `https://<production-домен>/api/cron/library-followups` |
| Метод | `GET` |
| Расписание | Каждые 5 минут / `*/5 * * * *` |
| Header name | `Authorization` |
| Header value | `Bearer <тот же CRON_SECRET, что задан в Vercel>` |
| Ожидаемый ответ | HTTP 200, JSON `ok: true`; `aiMap.disabled: false` при включённых флагах |

Использовать постоянный production-домен, не preview deployment. Секрет хранить в приватном поле заголовка scheduler, не в URL и не в репозитории. Не настраивать произвольные дополнительные вызовы для проверки: endpoint реально отправляет все наступившие сообщения. После настройки проверить историю выполнения внешней задачи и логи Vercel. Внешняя задача должна быть включена отдельно; один deploy её не создаёт. Интервалы сообщений зависят от фактических запусков scheduler.

Сроки отсчитываются от успешной отправки карты: +1/+3/+24/+48 часов. Первые два сообщения предлагают самостоятельную практику, последние два — личный разбор процесса. После четвёртого отправки заканчиваются.

Eligibility: карта завершена и показана, статус active/new, нет запроса разбора/handoff/qualified/converted, отказа и отключённых напоминаний. CTA и отказ сразу останавливают серию. Scheduler повторно проверяет состояние, атомарно фиксирует шаг **до** Telegram-send. Restart и параллельный cron не повторяют шаг. При 403 серия останавливается. При неопределённом результате отправки шаг не повторяется: лучше пропустить сообщение, чем продублировать. После длительного простоя отправляется только последний наступивший шаг, без пачки старых сообщений. Поэтому включение флага после паузы не перезапускает серию с первого сообщения.

Следующий обычный библиотечный reminder не планируется во время активной серии карты. Прогресс и ручное использование библиотеки доступны независимо.

## Events

Используется прежняя `user_events`, без отдельной аналитики:

- `ai_map_started`, `ai_map_completed`, `ai_map_result_shown`;
- `ai_map_material_clicked`: `material_id`, metadata `material_slug`;
- `audit_cta_clicked`;
- `welcome_video_sent`;
- `generated_visual_sent`: metadata `screen_key`;
- `ai_map_followup_sent`: metadata `step: 1 | 2 | 3 | 4`.

Старые audit/library/marketing events продолжают записываться. Отправка календаря не подтверждает бронирование и не создаёт converted state.

## Проверка Александром новым Telegram-пользователем

1. Использовать другой Telegram-аккаунт, которого ещё нет в CRM. Удаление чата с ботом не делает пользователя новым для сервера.
2. Отправить `/start`. Проверить кружок (если настроен), короткое обещание AI-карты, главную кнопку и две библиотечные кнопки.
3. Сначала открыть обе библиотеки без диагностики. В life проверить шар; открыть Telegraph-материал, отметить изученным дважды и убедиться, что прогресс/награда не удвоились.
4. Вернуться `/start`, нажать карту, ответить на пять вопросов. Проверить: три процесса, №1 с объяснением по своим ответам, конкретный ручной тест, реальные материалы. Сохранённую карту можно открыть повторно; серия не должна начинаться заново.
5. При включённых визуалах первый экран генерирует/сохраняет asset, следующее открытие использует file_id. Если provider недоступен, проверить наличие текста и кнопок. Для проверки ошибки лучше использовать отдельное тестовое окружение.
6. На одном тестовом аккаунте дождаться +1/+3/+24/+48 часов с работающим scheduler. На другом нажать CTA раньше первого сообщения: должен появиться вопрос о процессе, ответ должен сохраниться в CRM, затем — календарь; follow-up больше нет. Отдельно проверить `Не напоминать`.
7. Для безопасных ускоренных проверок использовать локальные mocked tests ниже, без изменения production timestamp и без массовых отправок.

```powershell
node --test tests/*.test.mjs
$env:TEST_AI_PROVIDER='qwen'; node --test tests/dialogue-journey.test.mjs
npm.cmd run lint
npx.cmd tsc --noEmit
npm.cmd run build
node scripts/verify-journey-migration.mjs
```

Последняя команда требует optional `@electric-sql/pglite` либо `PGLITE_MODULE` с абсолютным путём к его `dist/index.js`; работает в изолированной БД без production credentials. Webhook/image/Telegram проверки используют fetch mocks; file-storage проверка запускает два отдельных процесса и доказывает сохранение карты, claim и asset между restart. Live Telegram, image-provider, production Supabase и включённый cron требуют проверки после deploy.
